인지 부채 감사 — classical-text-browser

최초 감사 2026-07-04 · 2차 감사 2026-07-26 · 기준 v1.2.0 · 마지막 커밋 daa73e3(2026-07-26, 작업 트리 깨끗함) · 대상: hw725\classical-text-browser
모든 수치는 2026-07-26 실측(파일 직접 계수). 이 페이지는 AGENTS.md의 「인지 부채 지도」를 서술형으로 푼 것이며, 두 문서는 같은 순위·같은 경로를 쓴다.

1. 배경 — 왜 이 감사인가

이 프로젝트의 코드 대부분은 AI 에이전트가 작성했다. src/와 tests/의 Python·JS·HTML·CSS를 합쳐 183개 파일 96,642줄(2026-07-26 실측)이 존재하지만, 사용자(비개발자 CJK 인문학 연구자)의 이해는 문서에 적힌 지도 수준에 머물러 있고, 실제 영토(코드가 실제로 하는 일)와의 간극이 누적되고 있다. 이 보고서는 유지보수 문서(docs/유지보수문서/04_classical_text_browser.md)가 이미 다루는 내용은 반복하지 않고, 문서가 놓친 보이지 않는 코드 경로·암묵 관례·부수효과와 문서-코드 drift만 다룬다.

2차 감사에서 달라진 것. 최초 감사는 «어디가 이해되지 않았나»를 물었다. 넉 달 뒤인 지금은 답이 하나 더 생겼다 — 이 기간에 실제로 터진 결함은 전부 같은 모양이었다. 그 모양을 6절에서 따로 다룬다.

이번 판에서 다시 잰 값 요약 — 백엔드 Python 112파일 46,144줄, 프론트 38,550줄(index.html 4,821 + workspace.css 7,438 + JS 29파일 26,291), 테스트 39파일 11,948줄, API 라우트 183개(라우터 8개). .github/workflows는 여전히 없다.

2. 직관 — 이 앱을 한 문장으로 다시 보기

겉보기에는 «브라우저에서 고전 문헌을 열람·교정·번역하는 웹앱 하나»지만, 실제로는 최대 3개 프로세스(uvicorn 서버 + OpenAI OAuth 프록시 + 표점 Docker 컨테이너)가 배치파일 한 번으로 함께 기동되고, 결과물은 서고 폴더 안의 문헌별·해석별 독립 git 저장소 수십 개에 흩어져 기록되며, LLM 호출은 5단 폴백 라우터와 10분짜리 결과 캐시를 조용히 통과한다. «버튼 하나»의 뒤에서 무엇이 움직이는지가 이 감사의 핵심이다.

v1.2.0이 여기에 두 번째 얼굴을 더했다(D-055·D-060). 근현대 논문 스캔본을 끌어다 놓으면 8층 모델도 이중 저장소도 통과하지 않고 OCR → 검색되는 PDF까지 한 화면에서 끝나는 추출 모드다. 같은 서버·같은 데이터 구조 위에서 사이드바 아이콘이 8개에서 2개로 줄고 탭 절반이 숨는다. 즉 지금 이 앱은 한 코드베이스에 두 개의 서로 다른 사용 흐름을 얹고 있고, «화면에 없다»가 «코드에 없다»를 뜻하지 않게 됐다 — 이 구분이 4절과 6절의 밑바탕이다.

3. 핵심 흐름

텍스트가 원본 이미지에서 주석까지 흐르는 경로, 그 곁에서 모든 AI 기능이 통과하는 LLM 라우터 경로, 그리고 v1.2.0이 더한 추출 모드 지름길.

서버 기동 시 start_server.bat(178줄)이 (a) npx -y openai-oauth 프록시 자동 실행(포트 10531–10540 스캔, Bearer 토큰 oauth-proxy 하드코딩, 숨김 창), (b) punctuation-service/.env가 있으면 표점 Docker 자동 기동, (c) 2초 후 브라우저 자동 오픈까지 수행한다. «서버가 안 뜬다»의 원인이 셋 중 어디인지 아는 것이 디버깅의 절반이다. 끄는 스위치는 OPENAI_OAUTH_AUTO_START=0·PUNCT_AUTO_START=0.

5. 이번 기간의 유일한 패턴 — 오류를 내지 않고 틀리는 코드

D-063부터 D-069까지, 이 기간에 드러난 심각한 결함은 예외 없이 한 가지 모양이었다. 그럴듯한 틀린 답을 내놓고, 테스트는 전부 초록이고, 사람이 산출물을 실제로 열어 보기 전까지 아무도 몰랐다.

결정무엇이 조용히 틀렸나왜 안 잡혔나
D-068 텍스트 레이어 PDF가 텍스트를 0.24배로 쪽 왼쪽 아래 구석에 박았다. 넣으려던 12pt가 2.88pt로, 쪽의 60%를 덮어야 할 것이 4%로. 줄 수도, 좌표 계산도, 로그도 전부 맞았다. 원본 스캔 PDF가 0.24 0 0 0.24 0 0 cm을 q…Q 밖에 남겨 둔다(스캐너가 2064px을 495pt 종이에 맞춘 배율). 시험용 PDF를 PyMuPDF로 만들었기 때문에 그 스트림을 만난 적이 없다. 18개 시험 전부 초록.
D-069 ① 다권본에서 엉뚱한 권을 읽었다. 卷下 5쪽을 OCR 하면 卷上 5쪽 이미지가 엔진에 넘어가고, 오류 없이 그럴듯한 판독이 저장된다. 세 곳(image_utils.py·pipeline.py·llm_ocr.py)이 L1_source/*.pdf를 glob 해 첫 번째를 쓰고 part_id를 아예 보지 않았다. 테스트는 단권 문헌만 본다.
D-069 ② 사용자가 고른 LLM 모델이 무시됐다. 화면에서 «Claude로 돌려라»를 골라도 기본 폴백 순서대로 돌았다. L7 주석 AI 보조 4개 경로가 llm_router.force_provider = …로 존재하지 않는 속성에 대입했다. 파이썬은 없는 속성에 대입해도 조용히 만들어 준다 — 예외가 없다.
D-069 ⑤ 죽은 코드 약 1,000줄이 몇 달을 살아남았다. 「비교 모드」 880줄은 필요한 DOM id 8개가 index.html에 하나도 없었고, 「L5 종류」 라디오는 눌러도 아무 일도 일어나지 않았다. 죽은 참조 17건이 전부 if (!x) return으로 감싸여 있었다. 예외가 나지 않으니 «되지 않는다»가 «없다»처럼 보였다.
D-063 추출 패널의 「대조」·「영역」·「다음 미확인 쪽」이 아무 일도 하지 않았다. goToPage라는 함수가 애초에 없었다. typeof goToPage === "function" 가드가 삼켰다. 오류도 콘솔 경고도 없다. 게다가 검증에서 없는 함수를 가짜로 주입해 통과시켰다 — 스텁이 실제 계약과 어긋나면 테스트는 자기 자신을 검증한다.
D-066 «고쳤는데 화면에 반영되지 않는다» — 변하는 데이터를 캐시 지정 없이 읽는 GET이 47건. 브라우저가 캐시 기간을 스스로 추정했다. D-063에서 그 부류 한 곳(레이아웃 탭)만 고쳤다. 기계적으로 훑어 보니 같은 모양이 46곳 더 있었다. 한 곳을 고치고 끝냈으면 나머지는 사고가 날 때까지 남아 있었을 것이다.
교훈은 한 줄이다 — null 가드와 폴백은 실패를 침묵으로 바꾼다. 정말로 있어도 없어도 되는 것에는 옳은 도구지만, 반드시 있어야 하는 것에는 틀린 도구다. 없어야 정상인 것에는 가드를, 있어야 정상인 것에는 없으면 시끄럽게 알리기를 쓴다. D-063이 호출부의 «없으면 조용히 넘어가기»를 «화면에 알리기»로 바꾼 것이 그 적용이다.

그리고 «몇 줄 넣었다»는 시도의 기록이지 결과의 기록이 아니다. D-068에서 로그도 API 응답도 «30줄 제자리»라고 말했고 그것은 사실이었다 — 그 30줄이 어디에 얼마만 하게 놓였는지는 아무도 재지 않았을 뿐이다. 원본이 이미지뿐인 이상, 확인할 길은 결과물을 다시 열어 재는 것밖에 없다.
