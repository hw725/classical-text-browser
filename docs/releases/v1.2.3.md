# v1.2.3 릴리스 노트

날짜: 2026-09-02
범위: v1.2.2 이후 (D-079 ~ D-085)

## 한 줄 요약

**OCR 품질을 올리는 방식을 «프롬프트에 손으로 적기»에서 «저장소 안의 데이터로
조립하기»로 바꿨습니다.** 엔진 OCR 뒤에 LLM이 다시 보는 교정 패스가 생겼고, 추론
모델을 켜도 답이 비지 않게 예산 회계를 고쳤고, 이체자 사전에 층이 생겼습니다.
`korean-modern-document-ocr` 저장소와의 비교 분석에서 나온 결정들입니다.

되돌릴 수 없는 변화: **없음.** 기존 서고·문헌·해석 저장소는 그대로 열립니다.
`manifest.json`에 선택 필드 `ocr_guidance`가 추가됐고(없어도 동작), 문헌 안에
`variant_approvals.json`·`L4_text/correction_drafts/`가 **새로** 생길 수 있습니다.
설치 스크립트·의존성·`start_server`는 바뀌지 않았습니다. CPU·GPU 어느 쪽도 재설치가
필요 없습니다.

## 바뀐 것

### LLM 교정 패스 — 승급 사다리 (D-082)

엔진 OCR(Paddle·NDL) 결과를 그대로 두고, **다시 볼 블록만** LLM Vision에 넘깁니다.

| 단계 | 처리 | 추론 | 대상 |
|---|---|---|---|
| 0 | 엔진 OCR | 없음 | 전량 |
| 1 | 「LLM 교정(선별)」 — 블록 이미지 + 엔진 결과(앵커) | 끔 | 신뢰도 낮은 블록·협주·방주·한글 미지원 엔진 결과 |
| 2 | 「정밀 판독(선택)」 — + 앞뒤 블록·앞뒤 쪽 확정본 | 켬, 예산 분리 | 사람이 고른 블록 (행초·흘림체) |
| 3 | 사람 | | |

- 결과는 L2를 덮지 않고 **교정 초안**으로 저장됩니다. 초안 목록에 엔진 결과 →
  교정본, 앵커와의 일치율, 불확실 글자(`[?]`) 수가 보이고, **「적용」을 누른 블록만**
  L4에 들어갑니다. 적용은 현재 L4 위에서 그 블록의 엔진 원문만 바꾸므로 앞서 적용한
  블록과 손으로 고친 내용이 보존됩니다.
- 권 단위 일괄 OCR(추출 패널)에 「LLM 교정: 끔 / 선별만 / 전체」. 기본은 끔.
- API: 후보 조회·실행·적용 3개 (`.../ocr/correction-candidates`, `.../ocr/correct`,
  `.../ocr/correct/apply`).

### OCR 프롬프트 조립 (D-081)

LLM OCR 프롬프트가 다섯 조각으로 조립됩니다 — 고정 정책(보이는 대로·정규화 금지·
`[?]`·`□`·잡음 무시), 서지에서 만든 문헌 지침, L3 블록 종류, 문헌별 승인 이체자
쌍(주의 목록), 엔진 결과(앵커). 예전에는 페르소나 한 줄과 규칙 5개가 전부였고 블록
종류는 파이프라인에서 버려졌습니다.

- `manifest.ocr_guidance` — 이 문헌에만 해당하는 지침(인명·지명·자형)을 적는 자리.
  `PUT /api/documents/{doc_id}/ocr-guidance`.
- LLM이 `[?]`로 표시한 글자는 신뢰도 0.5, `□`는 0.1로 저장됩니다. 모든 글자에 0.9를
  박던 상수는 없어졌습니다. 마커는 텍스트에 남지 않습니다.

### 추론 모델 출력 보장 (D-083)

- 프로바이더 4종(Ollama·Gemini·OpenAI·Anthropic)의 비전 경로가 **사고 예산을 답변
  예산에 더해** 상한을 잡습니다. 사고가 상한을 삼켜 답이 비던 원인(D-074)이 이것입니다.
- 비전 경로도 JSON 형식을 실제로 강제합니다(Ollama `format` 스키마, Gemini mime,
  OpenAI `response_format`). 잘림(`done_reason`/`finish_reason`/`stop_reason`)과 빈
  JSON은 네 곳 모두 실패로 드러납니다.
- LLM OCR 엔진: 사고 켠 호출이 잘리면 **같은 프로바이더**에서 사고를 끄고 다시,
  그래도 잘리면 답변 예산을 두 배로. 잘림은 다음 프로바이더로 넘어가지 않으므로 로컬
  모델의 잘림이 유료 API 호출로 새지 않습니다. 사고문을 본문으로 쓰는 폴백은 없습니다.
- 기본값은 D-074 그대로 사고 끔. 사고를 켜는 것은 정밀 판독과 사용자가 명시한
  호출만입니다. OCR 요청 본문에 `llm_think`·`llm_thinking_budget`.

### 이체자 사전 3층 + 문헌별 승인 (D-080)

| 층 | 뜻 | 대조 화면 |
|---|---|---|
| strict | 확정 동자 (기본 사전, 이 문헌의 승인 쌍) | 이체자(노랑) |
| loose | 넓은 이체 관계 (교육부·漢語大字典 추출본) | 불일치 + «사전 힌트» |
| script | 간체·신자체 등 문자 체계 차이 (OpenCC) | 불일치 + «사전 힌트» |

- 동치는 strict만. 넓은 사전은 힌트일 뿐입니다 — 丘/业 같은 통가 관계를 동치로 치면
  오독이 숨습니다. 어떤 층의 사전으로도 본문은 바뀌지 않습니다.
- 대조 화면에서 불일치를 누르면 **「이 문헌에서 승인」**을 먼저 묻고,
  `documents/{doc_id}/variant_approvals.json`에만 저장됩니다. 전역 사전은 그대로.
- `scripts/build_variant_dicts.py`: OpenCC(Apache-2.0, 저장소 포함 4,423쌍)·Unihan·
  cjkvi-variants 원자료에서 사전을 만들고 파일마다 출처·라이선스를 기록합니다.
  cjkvi 계열은 라이선스가 확인되지 않아 로컬 전용(.gitignore).

### 정확도 재기 (D-084)

`scripts/eval_cer.py` — 사람이 확정한 L4를 정답으로 L2 엔진 결과와 교정 초안의 글자
오류율(CER)을 쪽별·엔진별로 냅니다. 프롬프트를 바꿨으면 이것으로 잽니다.

### 내용 트리 — TextBlock에서 쪽으로 (D-085 1단계)

사이드바에 **「내용」** 섹션이 생겼습니다. 해석 저장소를 고르면 Work → TextBlock을
순서대로 보여 주고, 블록을 누르면 그 내용이 있는 쪽(PDF)으로 이동해 해당 레이아웃
블록을 강조합니다. 두 쪽에 걸친 블록은 쪽 배지가 둘입니다. 지금 보는 쪽의 블록은
굵게 표시됩니다. 저장 형식은 그대로입니다 — 해석 층을 내용 단위로 저장하는 것은
2단계로 따로 결정합니다. API: `GET /api/interpretations/{id}/contents`.

### 그 밖에

- 문서 수치 드리프트 검사(D-079)가 pytest에 편입. 라우트 191개·테스트 47파일.
- **OCR 엔진 드롭다운이 «로딩 중…»에 멈추던 문제 수정.** 화면이 서고보다 먼저 열리면
  엔진 목록 요청이 500으로 끝나고 다시 부르는 곳이 없었다. 이제 서고가 정해질 때 다시
  불러오고, 기다리는 동안과 실패했을 때 그 이유를 드롭다운에 적는다(v1.2.2에도 있던 결함).
  같은 자리의 두 번째 결함: 엔진 하나의 상태 확인이 예외로 죽으면(Windows DLL 로드
  실패, cv2 배포판 충돌, `.env` 인코딩 오류 등) 목록 API 전체가 500이 되고 화면은 이를
  «서고 없음»으로 잘못 안내했다. 이제 깨진 엔진만 «사용 불가 + 이유»로 표시되고,
  초기화 예외는 원인 문구가 드롭다운·토스트에 그대로 보인다. `.env`는 BOM·cp949를 허용.
- README·사용자 안내서의 ZIP 링크를 기본 브랜치 `main`으로(옛 이름 리다이렉트 의존 제거).
- 사용자 안내서 §5.2-1~5.2-4 추가.

## 업그레이드 안내

- **할 일 없음.** ZIP을 새로 받아 풀거나 `git pull` 하면 끝입니다. 의존성은 그대로라
  `uv sync`도 다시 돌릴 필요가 없습니다(돌려도 무해).
- 새 기능은 전부 **선택**입니다. LLM 교정을 켜지 않으면 OCR 흐름은 v1.2.2와 같습니다.
- 이체자 사전을 더 넓히려면 `scripts/build_variant_dicts.py --opencc`(이미 포함) 또는
  `--unihan-zip`(unicode.org에서 Unihan.zip을 받아서)을 한 번 돌립니다.

## 알려진 한계

- **실제 모델 실측을 하지 못했습니다.** 개발 환경에 Ollama 서버와 API 키가 없어
  페이로드 조립과 응답 해석은 단위 시험으로만 고정했습니다. Ollama의 `format` 스키마가
  사고와 공존한다는 점과 Gemini 2.5의 토큰 회계는 문서 지식에 근거합니다. 첫 실측은
  D-074가 했던 것처럼 로컬 4B 모델 1쪽으로 response·thinking 글자 수를 재는 것입니다.
- 프롬프트 변경(자형 주의 목록, 블록 지침)이 CER을 실제로 낮추는지는 측정 전입니다.
  `scripts/eval_cer.py`가 그 도구이고, 사람이 교정을 끝낸 쪽이 있어야 잴 수 있습니다.
- 문헌 판독 지침(`ocr_guidance`)은 API로만 넣을 수 있고 화면 입력란은 아직 없습니다.
- 정밀 판독은 앞뒤 쪽의 **확정본(L4)** 을 문맥으로 쓰므로, 아직 교정하지 않은 문헌에서는
  같은 쪽의 앞뒤 블록만 문맥이 됩니다.
