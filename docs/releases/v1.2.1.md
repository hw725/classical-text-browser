# v1.2.1 릴리스 노트

날짜: 2026-08-12
범위: v1.2.0 이후 (D-073 ~ D-076)

## 한 줄 요약

**PaddleOCR 인식이 3.x에서 한 글자도 나오지 않던 것**을 고치고, 언어와 연산
장치를 고를 수 있게 했습니다. 함께 Ollama 비전 경로의 **잠재 결함 둘**도
막았습니다.

셋 다 오류를 내지 않고 그럴듯한 결과를 내놓던 자리라 자동 테스트는 전부
초록이었습니다.

## 고친 결함

### PaddleOCR이 한 글자도 읽지 못하고 있었다 (D-073) ★

`--engine paddleocr`로 돌리면 「OCR 실패 — 텍스트를 얹은 쪽이 없습니다」만
나왔습니다. 예외도 traceback도 없습니다.

원인은 결과 형식 판별 한 줄입니다.

```python
if not isinstance(raw_result, list) and hasattr(raw_result, "rec_texts"):
```

PaddleOCR 3.x의 `predict()`는 **이미지별 결과의 리스트**를 돌려줍니다. 그래서
이 조건이 언제나 거짓이 되어, 3.x 대응 코드(`_parse_v3_result`)가 **한 번도
실행되지 않고** 2.x 파서로 흘렀습니다. 2.x 파서는 dict를 순회하며 키(문자열)를
항목으로 받아 「구조 이상 — 건너뜀」 경고만 남기고 빈 결과를 돌려줍니다.

왜 오래 안 드러났는가 — 기본 엔진이 `llm_vision`이고 PaddleOCR은 **검출(위치)**
용으로만 쓰기 때문입니다. 인식 경로는 `--engine paddleocr`를 명시할 때만 타는데
도움말이 그것을 말리고 있었습니다. 사실상 사문화된 경로였습니다.

**검출(위치) 경로는 영향을 받지 않았습니다.** `line_detector`는 처음부터 3.x를
올바로 다루고 있었습니다 — 기존 사용자의 형광·드래그 위치는 정상이었습니다.

같이 고친 것:
- 결과 필드를 **속성·키 양쪽**으로 읽습니다. 판본에 따라 다르고, 한쪽만
  가정하면 조용히 빈 결과가 됩니다.
- `rec_polys`를 `dt_polys`보다 먼저 씁니다. `dt_polys`에는 검출만 되고 인식은
  안 된 것도 들어와 텍스트와 좌표의 짝이 어긋납니다.

### LLM이 «생각한 내용»이 PDF에 구워질 수 있었다 (D-074)

**조건이 맞아야 나는 잠재 결함입니다.** v1.2.0을 쓰면서 이 증상을 겪지
않았다면 조건이 걸리지 않은 것이고, 실제로 그러기 쉽습니다 — 아래 조건은
작고 약한 reasoning 모델에서 주로 성립합니다.

조건이 걸리면 본문 대신 사고문이 텍스트 레이어에 박힙니다.

> The user wants me to extract text from the provided image...

Ollama는 사고 흐름을 `thinking` 필드로 분리해 돌려줍니다. 프로바이더에는
「`response`가 비면 `thinking`이라도 쓴다」는 폴백이 있었는데, 일반 대화라면
무응답보다 낫지만 **OCR에서는 없느니만 못합니다.** 검색해도 안 잡히고 복사하면
영어 사고문이 나오는데 PDF는 멀쩡해 보입니다.

실측(qwen3.5:4b, 1쪽):

| | response | thinking |
|---|---:|---:|
| 예전(사고 기본값) | **0자** | 2,742자 |
| 지금(`think=False`) | **1,106자** | 0자 |

두 겹으로 막았습니다. OCR 호출은 `think=False`로 사고를 끄고, 그래도 빈 응답이
오면 `thinking`을 대신 쓰지 않습니다 — 빈 결과는 「실패」로 드러나기라도 하지만
이 오염은 드러나지 않습니다.

폴백 자체는 v1.2.0부터 있었고(`f452552`, 「빈 응답 방지」가 그때의 의도),
일반 대화에서는 무응답보다 나은 선택입니다. OCR에서만 반대로 작동합니다.

### 요청한 응답 길이가 무시되고 있었다 (D-075)

Ollama 비전 호출이 `max_tokens`를 인자로 받아 놓고 **payload에 넣지 않았습니다.**
응답이 모델 기본값에서 잘리고, 잘린 JSON은 파싱에 실패해 원문 JSON 문자열이
통째로 텍스트 레이어에 박힙니다. 그러면 줄 정보가 없어 한 덩어리로 얹히므로
형광·드래그 위치가 전부 무너집니다(실측: 서로 다른 y 위치 42개 → 1개).

## 더한 것

### PaddleOCR 언어·장치 선택 (D-076)

엔진이 레지스트리에서 인자 없이 생성돼 **언어와 장치를 바꿀 방법이
없었습니다.** 국한문 혼용 한국 논문에 중국어 간체 모델(`ch`)이 걸려 한글이
통째로 빠지는데도 손댈 수 없었습니다.

```
ctb ocr 논문폴더/ --engine paddleocr --paddle-lang korean --paddle-device gpu
```

환경변수 `CTB_PADDLE_LANG`·`CTB_PADDLE_DEVICE`로도 됩니다.

**장치 기본값은 `auto`입니다.** 설치된 paddle이 CUDA 빌드이고 장치가 실제로
보일 때만 GPU를 고르고, 그 외에는 전부 CPU입니다. **GPU가 없는 환경은 아무것도
지정하지 않아도 예전과 똑같이 동작합니다.** GPU가 있는데 CPU로 재보려면
`--paddle-device cpu`로 못 박습니다.

3.x는 `use_gpu` 대신 `device`를 받습니다. 이 인자를 넘기지 않고 있었으므로
그동안 `use_gpu` 설정은 3.x 경로에서 조용히 무시되고 있었습니다. 검출기
(`line_detector`)도 같은 선택을 따르게 맞췄습니다 — 이걸 안 맞추면
`--paddle-device cpu`를 줘도 검출만 GPU로 가서 「CPU로 재본다」가 성립하지
않습니다.

실측(RTX 3070 Ti Laptop, 200DPI, korean 모델): **CPU 52.1초/쪽 → GPU 1.0초/쪽.**

### PaddleOCR GPU 전환 절차 (선택 — 기본 설치는 그대로입니다)

**기본 설치는 v1.2.0과 같습니다 — 828MB, CPU판 `paddlepaddle`.** 이 판에서
의존성은 바뀌지 않았습니다.

GPU로 바꾸고 싶으면 절차를 [사용자 가이드](../user-guide.md)에 적었습니다.
두 배포판은 같은 `paddle` 모듈을 제공해 함께 설치할 수 없으므로 **교체**입니다.

```bash
uv pip uninstall paddlepaddle
uv pip install "paddlepaddle-gpu==3.3.1" --index-url https://www.paddlepaddle.org.cn/packages/stable/cu126/
```

**왜 기본값으로 올리지 않았나** — 실측하면 설치가 **828MB → 약 4.3GB**가 됩니다
(paddle 1,077MB + nvidia-* 런타임 2,708MB). `classical-gpu` extra(+4.5GB)와
맞먹는 덩치입니다. 이 저장소는 GPU 스택을 언제나 선택으로 두어 왔고, 그 방침을
패치 릴리스에서 뒤집지 않습니다.

바꾼 뒤 알아야 할 함정 셋을 문서에 적었습니다.

- **`uv sync`를 돌리면 되돌아갑니다.** 정본이 CPU판이므로 sync가 GPU판을
  지웁니다. sync 뒤에는 위 두 줄을 다시 실행해야 합니다.
- **Windows에서는 sync가 CUDA 런타임까지 지웁니다.** paddlepaddle-gpu 휠이
  nvidia-* 의존성에 `sys_platform == 'linux'` 마커만 달아 두었는데 Windows
  빌드도 그 DLL을 찾습니다. `cublas64_12.dll ... error code 126`으로 죽습니다.
- **`classical-gpu`와 함께 쓰려면 CUDA 버전을 맞춰야 합니다.** Linux에서 torch와
  paddle이 nvidia-* 런타임을 공유하며 서로 다른 정확한 버전을 고정합니다
  (torch cu124 → `nvidia-cublas-cu12==12.4.5.8`, paddlepaddle-gpu 3.3.1 →
  `==12.6.4.1`). 섞으면 의존성 해석 자체가 실패합니다.

## 알려진 한계

- **PaddleOCR 인식은 한글과 한자를 동시에 읽지 못합니다.** `korean` 모델은
  한글만, `chinese_cht`는 한자만 읽습니다(v1.2.0부터 알려진 것). 국한문 혼용
  문헌에서 `--paddle-lang korean`으로 돌리면 한자가 빠집니다. 실측 대조에서
  LLM Vision 결과 대비 문자 일치율 83.8%였고, 차이는 대부분 한자입니다.
  두 언어가 다 필요하면 인식은 LLM Vision에 맡기는 기본 조합을 쓰십시오.
- **작은 로컬 비전 모델은 구조화 출력을 끝내지 못합니다.** 4B 모델은 조밀한
  논문 한 쪽에서 JSON을 완성하지 못해 파싱에 실패하고, 그러면 줄 위치가
  무너집니다. 위 D-075를 고친 뒤에도 남는 모델 능력의 문제입니다.
- CUDNN 버전이 어긋납니다 — paddle은 9.9로 컴파일됐는데 핀은 9.5.1.17입니다
  (paddle 자신의 Linux 핀을 따랐습니다). 경고만 나오고 동작에는 문제가
  없었습니다.
- v1.2.0의 알려진 한계는 그대로입니다.
