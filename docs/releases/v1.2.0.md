# v1.2.0 릴리스 노트

날짜: 2026-07-26
범위: v1.1.5 이후 (D-055 ~ D-072)

## 한 줄 요약

근현대 논문 스캔본을 **끌어다 놓고 → OCR → 검색되는 PDF**까지 한 화면에서
끝내는 **추출 모드**를 더했습니다. 고서 교감 흐름은 그대로입니다.

## 추출 모드 — 논문 한 편을 위한 화면 (D-055 · D-057 · D-060)

기존 화면은 고서를 위한 것입니다. 상단 작업 탭 10개, 8층 데이터 모델,
원본·해석 이중 저장소 — 근현대 논문에서 텍스트만 뽑으려는 사람에게는
전부 통과 의례입니다. 추출 모드는 그 의례를 걷어냅니다.

- 문헌을 열면 **텍스트 레이어가 있는지 먼저 진단**합니다. 이미 있으면
  OCR 없이 바로 가져오고, 스캔본이면 OCR 경로로 안내합니다.
- 레이아웃을 사람이 잡지 않습니다. **쪽 전체를 한 블록으로** 자동으로
  잡아 저장합니다(D-067). 이상하면 레이아웃 탭에서 고치면 됩니다.
- 권 전체를 **한 번에** OCR 합니다. 이미 끝난 쪽은 건너뛰므로 중단해도
  이어서 돌아갑니다.
- 표점·현토·이체자·편성 탭이 숨습니다. 서고 백업·Git 이력 등 교감용
  설정도 함께 정리됩니다.

## 검색되는 PDF — 이번 판의 핵심 수정 (D-055 · D-062 · D-068)

원본 이미지 위에 **보이지 않는 텍스트**를 얹어 Ctrl+F·복사·서지 도구
연동이 되는 PDF를 만듭니다. 원본(`L1_source/`)은 읽기만 하고 결과는
`exports/`에 새 파일로 나갑니다.

- **줄 위치 검출**로 텍스트를 실제 글자 자리에 놓습니다. 좌표를 주지 않는
  LLM Vision 엔진에서도 형광이 원문 위에 뜹니다.
- **폰트를 임베드**합니다. 임베드하지 않으면 표준 CID 폰트에 없는 한자가
  조용히 사라졌습니다 — 실측에서 51종 130자(`郎` 27회, `儂` 22회)가
  누락됐습니다(D-062).
- **원본이 남긴 좌표 변환을 끊습니다.** 이것이 이번 판에서 고친 가장 큰
  결함입니다(D-068). 아래 「고친 결함」 참조.
- **만든 PDF를 앱이 다시 열어 잽니다.** 글자 크기, 텍스트가 덮은 넓이,
  그리고 표본 3쪽은 **그 자리에 실제로 글자가 있는지**(잉크 밀도)까지
  확인합니다. 이상이 있으면 내려받기 버튼 옆에 남습니다.
- 내려받는 파일 이름은 **원본 논문 파일명 그대로**입니다 —
  `저자_연도_제목.pdf` 규약이 깨지지 않습니다.

## 쪽별 검수 — 만들기 전에 확인한다 (D-057 · D-058)

- 「쪽별 검수」에서 **모든 쪽의 결과를 한눈에** 봅니다. 글자 수·줄 수와
  미리보기가 나오고, 빈 쪽이나 짧은 쪽에 표시가 붙습니다.
- 행을 누르면 그 쪽으로 이동하고 쪽 범위에 들어갑니다. 「대조」·「영역」
  버튼으로 교정 탭·레이아웃 탭에서 바로 확인할 수 있습니다.
- 확인한 쪽을 체크해 두면 PDF를 만들기 전에 **덜 본 쪽을 알려 줍니다.**
- LLM을 어느 모델로 몇 번 불렀고 얼마가 나갔는지 화면에 표시합니다(D-056).

## OCR 다시 돌리기와 되돌리기 (D-057 · D-064 · D-065)

- 레이아웃을 고친 쪽을 **기계가 찾아냅니다.** 그 쪽만 다시 돌립니다.
- 다시 돌리기 **직전 상태로 되돌리는** 버튼이 있습니다. 새 결과가 이전만
  못할 때 쓰는 수단입니다 — OCR 결과와 교정 텍스트를 함께 되돌립니다.
- 되돌리기는 로컬 JSON 백업입니다. Git 이력과 무관합니다.

## 설치와 실행 (D-059 · D-070)

**설치 용량을 실측해 적었습니다.** 그동안 어디에도 없던 숫자입니다.

| | 용량 | 언제 |
|---|---:|---|
| 기본 `uv sync` | **828MB** | 논문 추출은 이것만으로 전부 |
| `--extra japanese` · `classical` | +약 170MB | 일본어 문헌 · 고서 |
| `--extra classical-gpu` | **+약 4.5GB** | 고서 최고 품질 |
| 표점 서비스 (Docker) | 별도 | 외부 모델 · 선택 |

`classical-gpu`가 큰 이유: Windows는 CUDA 런타임이 별도 패키지가 아니라
`torch/lib` 안에 통째로 들어갑니다 — 그 폴더 하나가 4,359MB입니다.

`ctb` 명령과 웹 앱은 **같은 설치**를 씁니다 — CLI가 더 가볍지 않습니다.

**표점 컨테이너를 누구나 만들 수 있게 했습니다** (D-071). 베이스가 PyTorch
공식 CUDA 이미지라 GPU가 있으면 그대로 빌드됩니다. 이미 torch+CUDA 이미지를
갖고 있으면 `BASE_IMAGE`로 넘겨 재사용해 내려받기를 아낍니다.

오프라인 OCR 엔진 셋은 일본 국립국회도서관(NDL)이 CC BY 4.0으로 공개한
**NDLOCR-Lite** · **NDL古典籍OCR-Lite** · **NDL古典籍OCR Full**입니다.
설치 명령은 용도 이름(`--extra japanese`·`classical`·`classical-gpu`)을 쓰되,
문서에서는 엔진 이름을 앞세웁니다.

- **Python 3.12** 기준입니다(paddlepaddle 휠이 cp312까지). 3.10·3.11도
  그대로 지원합니다.
- 기본 설치에 **PaddleOCR**이 들어갑니다. 일본 고전적용 NDL 계열과
  GPU 스택은 extras로 분리했습니다 — `japanese`, `classical`, `classical-gpu`.
- **한 줄 명령**을 더했습니다. 서고를 미리 만들 필요가 없습니다.

  ```
  ctb ocr 논문.pdf
  ctb ocr 논문폴더/
  ```

- `opencv-contrib-python`과 `opencv-python-headless`가 같은 `cv2`를
  제공해 한쪽을 지우면 남은 쪽까지 깨지던 충돌을 해소했습니다.

## 문헌 구조 (D-061)

- 만든 뒤에도 **권을 더할 수 있습니다.** 사이드바 문헌 옆 `＋`.
- 단권 문헌은 트리에서 권 단계를 건너뛰고 쪽이 바로 나옵니다.
- 문헌 병합(따로 등록한 卷上·卷下 합치기)은 되돌릴 수 없는 작업이라
  실제 사례를 보고 설계하기로 하고 미뤘습니다.

## 고친 결함

### 텍스트 레이어가 0.24배로 박혔다 (D-068) ★

내려받은 PDF에서 드래그가 전혀 되지 않았습니다. 텍스트는 **있었지만** 495×694pt 쪽의 왼쪽 아래 구석에 2.0~2.9pt 크기로 들어가 있었습니다.

원인은 원본 스캔 PDF입니다. 스캐너가 2064픽셀을 495pt 종이에 맞추려고 파일 첫 줄에 `0.24` 배율을 적어 두는데, 그것을 되돌리는 표시가 없었습니다. 그 뒤에 덧붙이는 모든 것이 함께 줄어듭니다. OCR도 좌표 계산도 정상이었고 **마지막 써넣기 한 단계에서만** 끌려갔습니다.

시험용 PDF를 프로그램으로 만들어 썼기 때문에 자동 테스트가 이 상황을 만나지 못했습니다. 고친 뒤 실측(15쪽): 글자 7.4~32.6pt, 쪽의 62%를 덮고, 텍스트가 놓인 자리의 잉크 밀도가 쪽 평균의 **2.7~4.8배**. 이제 앱이 만든 PDF를 다시 열어 재고, 이상하면 알립니다.

### 조용히 틀리던 것들 (D-069 · D-072)

**오류를 내지 않고 그럴듯한 답을 내던** 결함들입니다. 자동 테스트는 전부 초록이었습니다.

| 무엇 | 증상 |
|---|---|
| 다권본에서 엉뚱한 권 읽기 | 卷下 OCR 하면 **卷上 이미지**가 엔진에 감 |
| 고른 LLM 모델 무시 | 「Claude로」 골라도 기본 순서대로 돎 |
| 비원자적 JSON 저장 | 저장 중 죽으면 **문헌이 통째로 안 열림** |
| 파일명·OCR 원문 미이스케이프 | 파일명에 스크립트를 넣으면 실행됨 |
| 상태바가 옛 버전 표시 | 버전을 적는 곳이 여러 곳이라 일부만 갱신됨 |

죽은 코드 약 1,000줄도 걷어냈습니다 — 화면 요소가 사라졌는데 `if (!x) return`으로 조용히 넘어가던 것들입니다. 해석 저장소 「비교 모드」(880줄), 눌러도 아무 일도 일어나지 않던 「L5 종류」 라디오 등. 「외부 파일을 새 문헌으로 가져오기」 화면은 죽은 코드가 아니라 D-037로 잠근 기능이라 남겼습니다 — 추출 모드의 「텍스트 바로 가져오기」와는 별개 경로이고, 그쪽은 정상 동작합니다.

**추출 모드 화면을 문서에 넣었습니다.** 스크린샷 17장이 전부 교감 모드였고, README 맨 위 그림이 탭 10개짜리 교감 화면이라 「추출 모드는 탭이 3개」라는 설명과 어긋났습니다.

### 그 밖에

- **레이아웃 탭에서 블록이 안 보이고 저장을 눌러야 나타나던 것**(D-067). L3 좌표계의 배율이 만든 주체마다 달랐습니다.
- **쪽을 옮기면 텍스트가 뜨기도 안 뜨기도 하던 것**(D-067). 늦게 도착한 응답이 새 쪽을 덮고 있었습니다.
- **고쳤는데 화면에 반영되지 않던 것**(D-066). 캐시 금지를 미들웨어 한 곳에서 붙입니다.
- **화면 여는 데 6.5초 걸리던 것**. `/api/llm/status` 6,572ms → 286ms.
- **표점 서비스 준비 상태**를 누르기 전에 보여줍니다 — 준비됨 / 시작 중… / 응답 없음.
- 「다음 미확인」 버튼이 동작하지 않던 것(D-063), 은퇴한 Ollama 모델을 계속 부르던 것(D-062), 추출 패널 아래가 잘리던 것(D-067), `--help`가 한국어 콘솔에서 죽던 것.

## 알려진 한계

- 좌표를 주지 않는 엔진(LLM Vision)에서 줄 위치 검출이 실패한 쪽은
  텍스트가 원문 자리가 아닌 곳에 순서대로 놓입니다. 검색은 되지만
  형광이 엉뚱한 데 뜹니다. 산출물 메타데이터에 `page-approximated`로
  기록되고 화면에도 알립니다.
- 앱 안의 PDF 뷰어는 텍스트 레이어를 그리지 않습니다. Ctrl+F는 내보낸
  파일을 외부 뷰어나 서지 관리 도구에서 열 때 동작합니다.
- 프론트엔드 자동 테스트가 없습니다(D-053). 이번 판의 화면 수정은
  jsdom 수동 검증으로만 확인했습니다.
- **외부 HWP·PDF 파일을 새 문헌으로 가져오는 화면**이 잠겨 있습니다(D-037).
  LLM으로 원문/번역을 분리해 넣는 흐름입니다. 백엔드는 살아 있고 화면
  진입점만 막혀 있습니다 — 복원 대상입니다.
  이미 등록한 문헌에서 **PDF 텍스트 레이어를 L4로 가져오는 것**은 추출 모드의
  「텍스트 바로 가져오기」로 정상 동작합니다(별개 경로).
- 문헌 병합은 미구현입니다.
