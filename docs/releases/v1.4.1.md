# v1.4.1 — cp949 콘솔에서 죽던 자리를 막습니다

날짜: 2026-09-22 · 범위: v1.4.0 이후

되돌릴 수 없는 변화 — 없음. 저장 형식은 바뀌지 않았고, 콘솔 출력과 설치 경로만 손봤습니다.

## 설치 (Windows)

1. 아래 **Assets**의 `CTB-Setup.exe`를 받아 두 번 누릅니다.
2. 설치 폴더와 글자 인식 엔진을 고르고 「설치」.
3. 「지금 실행」. 다음부터는 바탕화면 「고전서지 브라우저」 아이콘.

이미 깔린 PC는 `start_server.bat`을 켜면 저절로 새 판을 받습니다. macOS·Linux는 zip을 풀고 `./install.sh`.

## 무엇이 고쳐졌나

**환경 진단(`doctor.bat`)이 죽던 것을 고쳤습니다.** 한국어 Windows 콘솔의 기본 인코딩은
cp949인데, 한글은 cp949에 있지만 `—`·`«»`·`✓`는 없습니다. 그 글자를 찍는 순간
프로그램이 `UnicodeEncodeError`로 즉사합니다. `doctor.bat`은 **환경이 이상할 때 누르는
것**이라, 가장 필요한 순간에 파이썬 오류 화면이 떴습니다.

v1.4.0을 실제로 깔아 재현한 것:

```
UnicodeEncodeError: 'cp949' codec can't encode character '—'
  scripts\doctor.py line 21:  print(format_report(report, recs))
```

같은 자리가 있던 곳을 전부 찾아 막았습니다:

| 어디 | 언제 죽었나 |
|---|---|
| `scripts/doctor.py` | `doctor.bat`을 누를 때 |
| `scripts/warmup_paddle.py` | 설치 5단계에서 **모델을 못 받았다는 설명을 찍으려다** |
| `src/ocr/paddle_worker.py` | PaddleOCR 자식 프로세스 |
| `src/core/updater.py` | 새 판 확인 |
| `src/app/__main__.py` | 코드가 바뀌어 서버가 다시 뜰 때 |
| `CTB-Setup.exe` | 설치 프로그램의 `--help`·GUI 경로 |

**설치 프로그램(`CTB-Setup.exe`)은 이번에 처음부터 끝까지 실제로 돌려 확인했습니다** —
내려받기 → 압축 풀기 → 의존성 설치 → 글자 인식 모델 미리 받기까지 한 번에.

## 끌어다 놓기가 영문 이름 PDF를 거절하던 것

`report.pdf` 처럼 **영문 이름 PDF 한 장**을 창에 끌어다 놓으면
「같은 이름의 PDF가 두 번 포함되었습니다」로 거절됐습니다. 한 장만 넣었는데도
그랬고, 안내문이 원인과 무관해 스스로 풀 수 없었습니다.

원인은 이름이 겹친 것이었습니다 — 서버가 파일 이름에서 문헌 ID를 만드는데,
그 ID로 예약해 둔 이름과 올린 파일의 이름이 같아져 **자기 자신과 충돌**했습니다.
한글 이름은 다른 이름으로 저장되어 겪지 않았고, 그래서 오래 드러나지 않았습니다.

## 해석을 JSON으로 내보낼 때 오류가 나던 것

제목이 한글인 해석을 JSON으로 내보내면 **오류 화면**이 떴습니다. 내려받기
파일 이름에 한글을 그대로 넣었기 때문인데, 웹 표준상 그 자리에는 영문만
들어갑니다. 이제 표준 방식(RFC 5987)으로 한글 파일 이름이 그대로 내려옵니다.

이 저장소의 문헌은 제목이 거의 다 한글이라, 사실상 늘 실패하던 기능입니다.

## 개발자용

- `src/core/console.py` — 콘솔 고정을 한 곳에 모았습니다. 배포되는 진입점은 여기를 부릅니다.
- 이 종류가 다시 들어오지 못하게 검사를 여섯 붙였습니다: 배포 진입점이 고정을
  **먼저** 부르는가 · CJK 텍스트 계약(파일 인코딩·콘솔·정규식) · `.ps1`의 UTF-8 BOM ·
  설치 파일이 받는 판과 `pyproject`의 판이 같은가 · **영문 이름 PDF 한 장을 받는가**
  (이미지가 함께 올 때의 이름 예약은 그대로 지킨다) · **내려받기 헤더가 latin-1로
  인코딩되는가**(새 내보내기가 생기면 걸립니다).
- 「서고가 설정되지 않았습니다」를 500에서 **409**로 바꿨습니다(131곳). 서고가 없는 것은
  처음 켠 사람의 정상 상태이고, 500은 서버 잘못이라는 뜻이라 진짜 오류가 묻힙니다.
- `ruff` 위반이 늘지 않는지도 시험이 봅니다. v1.4.0 태그에서는 0건이었는데, 그 뒤
  아무도 부르지 않아 **64건**이 조용히 쌓여 있었습니다 — 전부 긴 주석·docstring 줄이라
  동작에는 영향이 없었지만, **이번 판에서 0으로 되돌렸습니다.** 시험의 기준선은 비어
  있고, 비어 있다는 것은 「어느 파일이든 0」이라는 뜻입니다.
